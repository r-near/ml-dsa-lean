# ML-DSA verify, round 13: stack, 32-bit targets, code identity, 2026-11-09

Branch `fv-p13` (from `fv-p12`, 5040dc5). Three questions: (1) can the Sign and KeyGen machine code of the default build be made identical to fv-p11's again
(the BINSEC evidence of rounds before 12 is about that code); (2) can the stack of verify come back down without losing the 32-byte-aligned single frame that
keeps the `+avx2` build stable across stack offsets; (3) does the 4-way verify pay on 32-bit targets. The proofs and gates are in `docs/assurance.md`, "Round 13".
Raw files of this round: this directory (`emu-instructions.txt`, `stackquick.txt`, `ab-run.txt`, `stack-scan.txt`) and `checkct/results/sweep-1d8b5c5/`.

## 1. Code identity with fv-p11 (Problem 1)

fv-p12's `ntt.rs` had no `mod dispatch`. fv-p11's had a plain safe wrapper module with five functions (`ntt`, `ntt_in_place`, `ntt_inverse`,
`ntt_inverse_in_place`, `multiply_ntt`) between the public functions and the `*_body` functions, plus an AVX2 variant behind the CPU check. This branch restores the module
(same names, same bodies, same module path, no choice inside) and deletes only the AVX2 variant. The hypothesis was that the wrapper layer, not the
removal of the AVX2 code as such, is what changed the inlining decisions in the callers of the NTT. It held: `checkct/compare-code.sh compare p11 p13f`
(the driver of `checkct/`, release, built on the build box with the pinned nightly; addresses are masked, see `checkct/compare_code.py`):

| target | functions in fv-p11 / this tree | identical | differ | only in one |
|---|---|---|---|---|
| riscv32imac-unknown-none-elf | 234 / 234 | 234 | 0 | 0 |
| thumbv7em-none-eabihf | 239 / 239 | 239 | 0 | 0 |
| x86_64-unknown-linux-gnu | 234 / 234 | 234 | 0 | 0 |

(fv-p12: 185 of 233, 107 of 236 and 39 of 233 functions differed.) The comparison is of the default release profile only, with addresses masked. It is not a
constant-time verdict and not a proof of equal behavior; the BINSEC runs of this round (`checkct/results/sweep-1d8b5c5/`) were made on this tree. The checkct driver
`#[path]`-includes `verify.rs`, `verify_arith.rs` and `api.rs`, and the verify-path functions are identical to fv-p11's in this comparison too, because the
driver does not call the 4-way verify functions that fv-p12 added.

`lean/Impl` for the NTT part is the form of fv-p11 again (the `ntt.dispatch.*` definitions are back), and `Proofs/NTT.lean`, `NTTInverse.lean` and `NTTOps.lean` are fv-p11's
files (their `unfold` lists mention `ntt.dispatch.*` again).

### What was tried

The goal was (a) stack no larger than fv-p11's, (b) `bench/stackscan.sh` OK with 0 paddings above 1.1 times the median in the `+avx2` build and the nearcore-flags build, (c) speed within 2 % of
fv-p12. The mechanism that decides (b) turned out to be one fact: the 4-way Keccak states spill 32-byte ymm slots, and LLVM aligns those slots to 32 only in a function that owns an explicit
`#[repr(align(32))]` local (`PreparedVk`, `VerifyScratch`). With the chain in one frame (`#[inline(always)]`), the frame is realigned and no slot straddles a 4 KiB page. A split in which the function that
runs the 4-way ExpandA has its own frame and only a `&mut PreparedVk` has a 16-byte-aligned frame, and the scan finds contiguous runs of slow stack offsets.
Experiments on the base 73c4976 (stackquick + `bench/scanboth.sh`, the default profile unless said otherwise; the painted/static default figures are for `verify_NN`):

| variant | change | `verify_NN` default KB | LTO static KB | stack-offset scan |
|---|---|---|---|---|
| base (this tree) | one frame, whole chain `#[inline(always)]` | 64 / 90 / 132 | 63 / 90 / 131 | OK, nearcore flags and `+avx2` |
| C | `verify_decoded` `#[inline(never)]` only | 65.6 / 92.7 / 134 | | `+avx2` OK; nearcore flags: one cell (65 `verify`) had 5/257 slow paddings (max 77.9 us against a median of 58.1; p90 58.3) |
| D | `prepare_vk_into_x4` `#[inline(never)]` only | 70 / 99 / 143 | | FAIL (`verify`, nearcore flags and `+avx2`) |
| E3 / E4 | both split | 55 / 82 / 121 | 50 / 74 / 112 | FAIL (`+avx2` and nearcore flags) |
| F1 | `api::verifying_key_*` = `VerifyingKey { inner: prepare_vk_x4(pk) }`, `prepare_vk_x4` (field-literal `PreparedVk { a_hat, t1_2d_hat, tr }`) `#[inline(never)]` | `verifying_key` 45.5 / 68.1 / 102.9 (base 49.7 / 74.3 / 111.0) | `verifying_key` caller chain 66.0 / 104.9 / 159.1 (base 49.6 / 74.2 / 101.7) | FAIL: nearcore flags `vk` 2 / 11 / 3 of 257 above 1.1 x median; `+avx2` `vk` 48 / 42 / 48 of 257 (slowest 66.8 against a median of 48.7 us for 87) |

E3 shows that the one-shot stack can come within 4 to 10 KB of fv-p11 (fat LTO 50 / 74 / 112 against 45 / 71 / 102) at the price of the scan; no variant removed the second key copy of
`verifying_key_87`: F1 builds the key in the shape of fv-p11's `prepare_vk` (a field-literal result of a non-inlined function), and the caller still holds a 66 KB key beside the
result under LTO (the wrapper row). The painted figures for E-variants in LTO builds are not used (the api function is inlined into the harness, section above); the table gives static figures.
`scripts/check-avx2-inlining.sh` also requires the 4-way permutation (`vpsllq ..%ymm` for 21 rotation amounts) inside each of `api::verify_NN`, `api::verify_internal_NN` and `api::verifying_key_NN` and a realigned frame
in each of the fifteen verify functions, so every split design (E3, E4, D, F1) would need that gate changed in the same commit, which is a weakening of the check, not a refinement.

**Decision.** Keep the single-frame design of 4d4bedb (this tree). Of the variants tried, none meets (a) and (b) together; (b) and (c) hold only here. The remaining stack growth over fv-p11 is
the price of the 4-way code that also takes 26 to 37 % off the one-shot verify time with nearcore's flags (38.6 / 57.9 / 96.2 us against 52.5 / 88.4 / 152.6 us, `2026-11-09-p12.md`). Recommendation by consumer: nearcore (fat LTO, no AVX2) pays +18 / +19 / +28 KB for `verify_*`,
a figure far below a thread stack, and gets a scan that is clean in its own flags and in `+avx2`; a consumer with a stack budget under 100 KB for verify, no AVX2 and no concern for layout can take
variant E3 (not committed; it is the split of `prepare_vk_into_x4` and `verify_decoded` described above) and accept scan failures in a `+avx2` build.

## 3. 32-bit targets (Problem 3)

overflow checks on; ARM: `thumbv7em-none-eabi` with `-Ctarget-cpu=cortex-m4`, software float; RISC-V: `riscv32imac-unknown-none-elf`; no SIMD on either).
