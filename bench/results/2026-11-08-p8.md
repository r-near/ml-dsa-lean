# ML-DSA verify, round 8: the dispatch and the 4-way Keccak enter the proof, 2026-11-08

Branch `fv-p8` (from `fv-vec`). Two things changed for the proof and nothing for the speed:

* `Proofs/Keccak4.lean` now proves `round25`, `lane_rounds2` and `keccak_f1600_x4` equal to four scalar `keccak_f1600`
  directly on the plain-Rust 4-way Keccak. The lane-operation specs and the `Sh4` instance are gone.
* The AVX2 dispatch is extracted and proved. `fast_verify` has three crate-private `_with` functions that take an
  `Option<cpu::Avx2>` token; `api.rs` has fifteen `NAME_with` functions and every public function is one line that passes
  `cpu::avx2()`. `Proofs/Dispatch.lean` proves, for every value of the token (so for whatever the CPU check returns), that
  each `_with` function equals the scalar function it replaces, as `RustM` values including divergence.

The numbers below show the performance of the final tree against `fast-verify` and `fv-vec`.

Built and run as in [2026-11-07-p7](2026-11-07-p7.md): nearcore profile and target features (no AVX2), one pinned core of
an AMD EPYC 9B14 (Zen 4, KVM guest) at a measured 3.40 GHz, rustc 1.99.1, ASLR off, load about 1.

## A regression found and fixed on the way: the prepared-key verify

The first version of this round removed `align_frame()` (the `black_box` stack-alignment anchor) everywhere and gave the
two wrappers that own a `PreparedVk` the alignment through `#[repr(align(32))]` on the type. The first A/B then showed the
prepared-key verify 2% to 8% slower than `fast-verify` (pad 0, µs; p8 at the first version of the tree):

| set | fast-verify | fv-vec | p8, no anchor | p8 / fast-verify |
|---|---|---|---|---|
| 44 | 9.78 | 9.80 | 10.01 | +2.4% |
| 87 | 15.10 | 15.10 | 16.44 | +8.9% |

`verify_prepared_avx2` only borrows the key (`&PreparedVk`), so the type's alignment does not give its frame any. Building
the variant with the anchor back in `verify_prepared_avx2` (and nothing else changed) restored parity; that variant is the
final tree. `align_frame()` is a value-free call there: empty under `--cfg miri` (the extraction), a stack-alignment anchor
otherwise, taking and returning no data, so the proof is about the same function body. The one-shot wrapper and
`prepare_vk_avx2` own their key (a `PreparedVk` local) and are aligned by `repr(align(32))` alone; the interleaved A/B above
shows them at parity without any anchor. (A control variant without `repr(align(32))` on the type was also built; its numbers
were not kept.)

The stack-offset scan below cannot see this: it measures the spread over paddings of one binary, and the regression was a
uniform shift of the whole distribution. Only the interleaved A/B against the previous binary shows it.

## Object code

`scripts/check-avx2-inlining.sh` requires all nine wrappers (three operations times three sets) to be realigned and the 4-way
permutation to be vectorized in each: `OK: 4-way permutation vectorized in every wrapper; verify-only arithmetic fully
inlined; verify wrappers realign their frames; 57465 lines of ymm code`. That LLVM vectorizes the Keccak loop is a
performance property, checked here; the proofs do not assume it.
