# ML-DSA verify: AVX2 wrapper for the prepared-key verify, 2026-11-07

Branch `fv-p5` (from `fast-verify`, which has the p4 verify-only arithmetic). One speedup kept: the prepared-key verify
(`verify_prepared_NN`, `verify_internal_prepared_NN`) is compiled with AVX2 through a second `#[target_feature(enable =
"avx2")]` wrapper around the proved scalar function. No intrinsic, no 4-way variant, no new `Lanes4` method, no new Lean
theorem: the function that runs is the extracted one (`Proofs/PreparedVerify.lean` and `Proofs/Verify.lean` apply as
they are). Everything else that was tried either measured as no gain or needed a new proof for under 1.5 µs, and is listed
below.

Built and run as in [2026-11-07-p4](2026-11-07-p4.md): nearcore profile and target features (no AVX2), one pinned core of
an AMD EPYC 9B14 (Zen 4, KVM guest, zero steal), cpu 45 for the default toolchain (rustc 1.99.1), cpu 46 for 1.95.0
(nearcore's), load about 1 (the benchmark itself, plus another job on the box). Medians of 15 rounds, microseconds.
Raw logs (build-tool lines and local paths removed): [`fast-verify-p5.log`](2026-11-07-p5/fast-verify-p5.log) (rustc 1.99.1, the
second of two runs), [`fast-verify-p5-run1.log`](2026-11-07-p5/fast-verify-p5-run1.log) (rustc 1.99.1, the first run) and
[`fast-verify-p5-195.log`](2026-11-07-p5/fast-verify-p5-195.log) (rustc 1.95.0).
Provenance of the table in `docs/assurance-history.md` section 5: the 1.99.1 columns are the second run (`fast-verify-p5.log`) except the
`avx2` one-shot ML-DSA-65 cell (42.4), which is from the first run (`fast-verify-p5-run1.log`): the second run hit a slow stack
offset there (49.9) and the first run hit one for the `avx2` one-shot ML-DSA-44 cell (30.4; the second run has 26.7). The
interleaved A/B below is the tiebreaker (42.74 against 42.39). The 1.95.0 columns are one run.

## Run-to-run layout effect: the numbers of one binary can move by 7 to 12 µs

Two `fast-verify.sh` runs of the same tree gave, for the `avx2` one-shot verify, ML-DSA-44 30.4 µs in the first and 26.7 in
the second, and ML-DSA-65 42.4 in the first and **49.9** in the second (min 49.7, max 50.0 over the 15 rounds, so it is
stable, not noise). The cause is the position of the stack: the process environment (here, the length of the build
directory name) moves the stack start, and at some offsets the one-shot verify is 7 to 12 µs slower. Running one binary
with a padding variable of growing length in its environment (ML-DSA-65 one-shot verify, µs, `taskset`, pinned):

```
pad bytes   0     8     16    32    64    128   256   512   1024  2048  3072
p5 build    42.1  43.3  42.4  42.4  42.0  54.7  42.1  42.1  43.1  42.4  52.3
```
and a finer scan (pad: µs)

```
fast-verify base (9507aa5)  0:42.2 64:42.9 96:42.6 112:49.2 128:52.1 144:42.3 160:42.2 192:42.4 224:43.4 3072:42.4 3104:42.3
this branch                 0:42.3 64:43.0 96:43.0 112:49.7 128:42.7 144:42.6 160:42.1 192:50.6 224:42.4 3072:42.5 3104:42.1
```

The base shows it too, so the effect is older than this branch. The cause was not isolated (the AMD part has no
`ld_blocks_partial.address_alias` counter; a store-to-load forwarding or 4K aliasing effect between stack buffers is the
likely one). The wrapper added here neither causes nor fixes it. About one offset in six or seven costs 7 to 12 µs. For a
real process the offset is whatever the caller's stack is. It is the largest single item found that is not in the list
below and it needs its own investigation (the first thing to try is aligning the large stack arrays, which changes types
and therefore proofs). The table in the assurance case uses, for the `avx2` one-shot ML-DSA-65 cell, the first run's 42.4
(which agrees with the interleaved A/B above, where both binaries run in the same environment).

## Where the 43 µs of ML-DSA-65 goes (pprof, one-shot, `avx2`)

ExpandA 22 µs (4-way Keccak 15.8), `hash_pk` 5.45, c̃' hash 3.3, the NTTs about 5.4, multiply-accumulate, NTT⁻¹ and UseHint
about 4.3, decoding about 1.7. Stage timings and the hot-code check (all of it in the ymm region) are from
`bench/profile.sh`.

## Tried and dropped (no gain outside noise)

Each measured on the public API, interleaved, pinned, five passes. None is in the branch.

| Attempt | Result |
|---|---|
| `#[inline(always)]` on `sig_decode`, `unpack_signed`, `pk_decode`, so that the decoders compile inside the wrappers | stage timings 921 to 843 ns and 771 to 705 ns, nothing outside noise in the A/B |
| ExpandA fast path for the common case (first block covers all 256 candidates), slow path inline | `verifying_key` +10 µs, no one-shot gain |
| the same with the slow path `#[inline(never)]` | the regression is gone, no gain either |
| verify-only SHAKE: Keccak-f[1600] unrolled by hand (θ, ρ, π, χ, ι as straight-line code, ping-pong between two states) and block-wise absorb, for `hash_pk`, μ and c̃' | one-shot 65: 42.94 to 44.27; prepared 12.00 to 11.83; `verifying_key` 33.20 to 34.04. Slower or equal, so no proof was written |
| scratch prototypes of fused NTT layers, an unrolled single-lane Keccak and a faster ExpandA parse | each better than the baseline in an isolated stage loop by 0.3 to 1.5 µs and not reproducible in the real build |

## Skipped: would weaken the proof

Estimates are rough and unmeasured: a share of the profile above times a guess at what the technique gives elsewhere.

| Item | Why it is skipped | Estimated gain (ML-DSA-65 one-shot) |
|---|---|---|
| hand-written AVX2 NTT and NTT⁻¹ | new intrinsics and new trusted code next to the proved arithmetic | 1.5 to 2.5 µs |
| AVX2 single-state Keccak for `hash_pk`, μ and c̃' | new intrinsics | 2 to 3 µs |
| new `Lanes4` methods (a fused θ or χ step, a rotate by arbitrary amount) for ExpandA's 4-way permutation | enlarges the tested-not-proved instance | 1 to 2 µs |
| an 8-way ExpandA (8 lanes) | a new lane type with new intrinsics | 2 to 3 µs |

Skipped for proof cost, not because they weaken it (each under 1.5 µs in a prototype, needing a new equivalence proof of
new extracted code): a fused ExpandA parse and unpack, fused NTT layers, an unrolled verify-only Keccak.
