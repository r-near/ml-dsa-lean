# ML-DSA verify, round 12: no run-time dispatch, 2026-11-09

Branch `fv-p12` (from `fv-p11`, 1a8d3e2). Round 12 removes the run-time AVX2 dispatch: verify always calls the 4-way code
(`verify::verify_internal_x4`, `prepare_vk_into_x4`), and the NTT dispatch of Sign and KeyGen goes in separable commits at the end of the branch, so
that the crate has no `unsafe` and detects nothing at run time. This file has the measurements behind the design choice (Phase 1) and the cost of the
removals. The proofs and gates are in `docs/assurance.md`, "Round 12".

Method. `bench/ab.sh` style: the bench binary of each variant built with the `nearcore` profile of `bench/Cargo.toml` (overflow checks on, as in `bench/ab.sh`) and the flags named in the column, one pinned core of the build box (AMD EPYC 9B14, Zen 4, about 3.4 GHz measured, rustc 1.99.1), ASLR off, no
environment padding, binaries interleaved so that other load hits all alike (loadavg about 3 at the start of the runs; the box was not idle).
Each cell is the median over the per-pass medians of 4 passes of 7 rounds each (`out-*-pad0-*.tsv`). Times are µs per call.
`nc` is nearcore's flags (`-Ctarget-feature=+sse2,+ssse3,+sse4.1,+sse4.2,+popcnt,+fma,+bmi1,+bmi2,+lzcnt,+movbe,+pclmulqdq
-Cforce-unwind-tables=y`, no AVX or AVX2); `nca` is `nc` plus `-Ctarget-feature=+avx,+avx2`; `base` is no flags (baseline x86-64).
`s` is the scalar verify (`verify_internal`, `prepare_vk`), `x` the 4-way verify. The second letter says whether the verify-only arithmetic is
`#[inline(always)]` (`i`, what the old dispatch wrappers forced) or left to the compiler (`n`).

The verify chain is `#[inline(always)]` from the public functions down to the permutation (the same functions fv-p11 inlined in its AVX2 wrappers). This costs stack
against a tree where the callees keep their own frames (measured on the way here: `verify_NN` 56 / 80 / 118 KB without the attribute, 64 / 90 / 132 KB with it), and it is kept because the
frames then stay 32-byte aligned with every 256-bit spill slot in one frame; without it, a build with AVX2 target features showed 34 of 257 stack offsets more than 1.1 times the median
(`bench/stackscan.sh`; callee frames that are only 16-byte aligned straddle 4 KiB pages at some offsets).

One-shot verify grows by 19 to 21 KB in the default profile (+19 % to +43 %; the 4-way Keccak holds four 200-byte states, the sampler four SHAKE128 outputs, and the inlined chain
does not share frame space between its stages). The growth that needs a word is `verifying_key_87` (+76 KB in the default profile, +9 KB under LTO against fv-p11's 93 KB).
`verifying_key_NN` is written to build the key in the result slot
(`let mut vk = PreparedVk::zeroed(); prepare_vk_into_x4(pk, &mut vk); VerifyingKey { inner: vk }`), but the compiler does not elide the local `vk`: the extra 76 KB is
about one more `PreparedVk` of ML-DSA-87 (65,600 bytes) on the stack, so the key exists twice. The 44 and 65 growth (+15 and +17 KB) is of a different size
and is not explained by a second key. fv-p11's 35 KB for `verifying_key_87` was the build-in-place figure. Source rewrites that tried to restore the
in-place construction did not remove the copy and were dropped (nothing of them is in the tree). **This is not fixed in this round**, and it is the one stack regression of the round that a reader
needs to know about: the documented budget for `verifying_key_NN` is now 50 / 74 / 111 KB below the caller's frame (default profile, rustc 1.99.1) plus the returned key in the
caller's frame. A follow-up that fills the matrix in the key by value in the x4 ExpandA would be the next thing to try.

Under `lto = "fat"` (nearcore's release profile) the static walk gives 63 / 90 / 131 KB for `verify_NN` (+18 / +19 / +28 KB) and 50 / 74 / 102 KB for `verifying_key_NN` (-6 / -20 / +9 KB).
**Withdrawn in round 13:** the sentence that stood here (a painted harness binary under LTO of 259 / 313 / 399 KB for `verify_NN` against 70 / 103 / 170 KB for fv-p11, cause not traced) quoted the dev-profile (opt-level 0) block of the output of `tools/stack/run.sh`. A painted release build with fat LTO gives 63.0 / 89.7 / 130.6 KB, the static walk (`bench/results/2026-11-09-p13.md`). All figures are far below a thread's megabytes of stack, but a reader who sets a tight stack budget under LTO should measure their own binary.

The attribute is what keeps the 256-bit spill slots in one realigned frame: without it, callee frames that are only 16-byte aligned straddle 4 KiB pages at some stack offsets. That matters for builds with `+avx2` and
not for nearcore's current flags. nearcore's release profile is fat LTO with one codegen unit, where the attribute costs the larger stack above. This tree keeps the attribute, because its AVX2 speed is stable across stack offsets and the documents advertise it; this is a performance and stack choice, not a proof one (the proofs are about the Rust text, which differs only by the attribute). Reverting 4d4bedb (and the matching figures) is the alternative for a consumer who builds with nearcore's flags only.

The thumbv7em figures are the repo's measurement for the embedded target and agree with x86_64 within 1 %.

## Sign and KeyGen: the cost of removing the NTT dispatch for `avx2`-feature users

`o` is fv-p11 plus nothing (the dispatching NTT of 0.1.0's `avx2` feature, built with `--features avx2`), `n` is the final tree of this branch (the feature is a no-op); `1` is nearcore's flags, `2` is nearcore's
flags plus `+avx,+avx2`. Medians of 3 runs of 7 rounds, one core, µs per call; "change" is `n / o`. Users who did not enable `avx2` ran the portable NTT before and after: no change for them (the
default-profile verify/sign/keygen code comparison is in the next section).

An `avx2`-feature user whose build has no AVX2 target features (nearcore's flags) loses 14 to 17 % of Sign time and 2 to 6 % of KeyGen time; with `+avx2` target features
there is no difference beyond noise (-1.9 % to +1.1 %), because LLVM vectorizes the one portable NTT the same way the dispatched copy was compiled. The fix for the
first case is the build flag (`-C target-feature=+avx2` or `-C target-cpu=x86-64-v3`), not a feature of this crate.

## The code of the default build

`checkct/compare-code.sh` (masked disassembly of the checkct driver, `release` profile, riscv32imac, thumbv7em and x86_64) between fv-p11 and two trees of this branch:

- the verify commits only (4fe6198, 4a67f78; the NTT dispatch still in `src/ntt.rs`): **234, 239, 234 functions, every one identical, none added or removed.** The Sign
  and KeyGen code of the default build did not move when the verify dispatch was removed.
- the final tree (NTT dispatch removed too): x86_64 233 functions (one fewer), 194 identical and 39 differing; riscv32imac 233, 48 identical and 185 differing; thumbv7em 236, 129
  identical and 107 differing. The differing functions are the NTT callers of Sign and KeyGen (`matrix_vector_ntt_into`, `scalar_vector_ntt_inverse_into`, `response_into`,
  `hint_step_into`, `prepare_sk_into`, `sign_internal`, ...): with the dispatch gone the NTT bodies inline differently. So the default build's Sign and KeyGen object code
  is **not** unchanged by the NTT commit, and the BINSEC evidence for it is rerun on the final tree (`docs/assurance.md`, section 4, "Round 12").
