# Benchmarks, 2026-11-06: ml-dsa-lean against other ML-DSA implementations

Measurement only: nothing under `src/` changed. All three parameter sets, on one pinned core of a shared build box.
Raw TSVs and logs are in [`2026-11-06/data/`](2026-11-06/data/). Times are microseconds per call unless stated.

## Summary

- **Portable code is the weak spot, and its numbers depend on process state (see "Process state").** In a fresh process this
  crate's default build signs 1.6-1.7x slower than mldsa-native's portable C and verifies 1.4-1.5x slower; in a process that
  has already run mldsa-native's AVX2 code the same build is 1.2-1.3x behind on sign and 1.15-1.3x on verify. Keygen, which the
  process state does not touch, is 1.4x behind in both states. Both states are measured and reported below; this file does not
  pick one.
- **With AVX2 the gap is 3.2-4.2x.** The `avx2` feature (NTT only) is 3.7-4.1x behind mldsa-native AVX2 on sign, 3.2-3.5x on
  verify, 3.3-3.6x on keygen. Built with `-C target-cpu=x86-64-v3` it is 2.8-3.6x behind. libcrux AVX2 is 1.6-2.0x behind
  mldsa-native AVX2; aws-lc-rs is within 1.04-1.3x of mldsa-native AVX2 on keygen and verify and close to libcrux AVX2 on
  (hedged) sign.
- **Prepared keys help**: prepared-key verify is 2.2-2.8x faster than uncached verify in the default build and 3.0-4.6x with
  AVX2 or x86-64-v3, and prepared-key sign saves 15-33%. Only RustCrypto (cached expanded key) and aws-lc-rs (a parsed `PqdsaKeyPair`) have something comparable.
- **Profile**: the AVX2 gap is scattered. Against mldsa-native AVX2 (ML-DSA-65 sign) this crate spends about 2.2x the time in
  Keccak, 3x in the NTT, 8x in pointwise work, and roughly 70x in rounding/hints/norms (123 us against 1.7 us), where the
  profile points at scalar constant-time helpers (`field::ct_select`, `wrapping_sub`, `small_reduce`).
- Compared with the 2026-10-31 figures in `docs/assurance.md`, this crate is about 0-13% slower on the same box while the
  competitors are unchanged (see "Comparison with 2026-10-31").

aws-lc-rs differences, all visible in `bench/src/cells.rs`: signing is hedged (fresh randomness inside, no way to pass a
fixed `rnd`), so there is **no deterministic sign** row and its sign output differs from call to call; the API has no context
parameter, so only the empty context is measured; keygen is `PqdsaKeyPair::from_seed` plus the public key bytes (the
`+sk-export` row adds exporting the raw secret key, which is part of the other implementations' keygen output; 0.5-1 us);
sign builds the key from the raw secret key on every call (like the other uncached rows; this is how nearcore calls it) and the
`+cached-sk` row signs with an already-built `PqdsaKeyPair`; verify is `UnparsedPublicKey::new(..).verify(..)` on every call.
Before timing, the harness checks once that aws-lc's key from the seed equals ours and that its signature verifies under our
public key and its verify accepts our deterministic signatures. Because signing is random, the number of rejection attempts
varies with the draw. Over the 256 messages the other implementations all sign the same bytes, with a mean of 4.29 / 4.95 /
3.51 attempts per hedged signature for ML-DSA-44 / 65 / 87 (4.57 / 5.15 / 4.11 for the deterministic one, from
`bench/src/bin/micro.rs`). aws-lc-rs averages over many draws, i.e. FIPS 204's expectation of 4.25 / 5.1 / 3.85. So the aws-lc-rs
hedged sign figure is about 1% too low for -44, 3% too high for -65 and 9% too high for -87 relative to a message set with the
same mean as ours (approximate: it scales all time with the attempts). Run to run its spread over rounds is 5-9% at the default
round length and at most 2.2% with 1.5 s rounds (`data/aws-long-rounds.tsv`; the sign medians agree with the short rounds within
1% for -44/-65, 3% for -87).

## Process state: a fresh process is slower for portable Rust code

`bench` measures all implementations in one process, cells ordered keygen, sign, verify. Portable code in this crate and in
RustCrypto runs **much slower in a process that has not yet executed mldsa-native's AVX2 code** than after one has:

| ML-DSA-65, deterministic sign | fresh process | after `mldsa-native-avx2` ran in the process |
|---|---|---|
| ours, default | 791 | 585 |
| ours, `avx2` feature | 391 | 390 |
| RustCrypto | 1110 | 746 |
| libcrux portable | 512 | 496 |
| mldsa-native portable | 459 | 451 |

Established, all on CPU 1, all with the same 3.40 GHz measured clock:

- The trigger is a cell of `mldsa-native-avx2` (keygen is enough) running earlier in the process. `mldsa-native-portable`,
  RustCrypto, libcrux portable and aws-lc-rs cells running first do not trigger it; a `libcrux-avx2` cell triggers part of it
  (768 us).
- Not ASLR (`setarch -R`), not argument or environment size, not stack depth (touching up to 8 MB of stack first changed
  nothing), not the clock, and not simply executing one 256-bit instruction and `vzeroupper` (`bench --prime-avx2`: 789 us
  with the flag, 789 without).
- The extra time is in the NTT. Sampling profile of ML-DSA-65 sign, default build, microseconds per call (profiler overhead
  included; same binary, `prof` from `bench/profile.sh`): fresh 794 total = Keccak 138, **NTT 354**, pointwise 142,
  rounding 141; after AVX2 589 total = Keccak 135, **NTT 159**, pointwise 136, rounding 139. ML-DSA-87: NTT 409 against 181
  (total 990 against 755). Verify: NTT 43 against 20 (-65), 57 against 26 (-87).
- Builds with VEX-encoded vector code are not affected: the `avx2`-feature build and the `-C target-cpu=x86-64-v3` builds of
  this crate and of RustCrypto show the same numbers in both states (within 3%). Only the baseline-x86-64 (SSE2) builds of
  the Rust crates are. There is no hardware-level explanation yet (`perf` is not available to unprivileged users here: paranoid = 4).
  It is a property of this KVM guest and these builds as measured, so it may or may not appear on a node's hardware.
- Fresh-process medians are stable between two repetitions (largest difference 1.6% for the default build, 2.9% for the
  `avx2` build); the libcrux x86-64-v3 rows differ by up to 7.3% between two fresh processes, so treat those rows as +-7%.

So there are two states, and both are real measurements:

- **fresh process**: each implementation alone in a new process pinned to the core (`bench/isolated.sh`; this is the
  "one implementation at a time" rule taken literally). Two repetitions, mean of the two medians.
- **in-process, after AVX2**: the single-process `bench` run as `compare.sh` does it (`data/inprocess-*`). Keygen cells of the
  first implementations run before any AVX2 code, but keygen is not affected. Two repetitions, mean of the two medians.
  The `docs/assurance.md` figures of 2026-10-31 came from the same `compare.sh` ordering, so its default column was measured in
  the in-process state (keygen as the first cell, before any AVX2 code; sign and verify after it).

Which one a node sees depends on whether other AVX2 code (aws-lc-rs itself, for one, or anything else in the process) has run;
that is for the reader to decide.

## Results

How to read the tables: rows are grouped as portable (no AVX2 code), AVX2, and the Rust crates rebuilt with
`-C target-cpu=x86-64-v3`. The C libraries are not affected by `RUSTFLAGS`, so they are listed once. "prepared key" is
`signing_key_NN` / `verifying_key_NN` for this crate, the expanded key for RustCrypto and a built `PqdsaKeyPair` for aws-lc-rs.
`n/a`: the implementation has no such operation (libcrux and mldsa-native have no prepared-key API; aws-lc-rs has no
deterministic sign and no prepared verify). Ratios are time of this crate divided by the time of the fastest other
implementation of the same class (above 1 means this crate is slower; below 1 means faster); the name in brackets is that
implementation. Portable-versus-portable and AVX2-versus-AVX2 comparisons are the first and second groups of rows.

## Spread and repeatability

- Spread = (max - min) / median over the 15 rounds. In-process runs: at most 1.8% for every row except aws-lc-rs hedged sign
  (6.9-9.6%, explained above; at most 2.2% in the 1.5 s-round run) and one outlier (this crate's prepared-key hedged sign,
  ML-DSA-65, 6.4% in the second `default` run); the median over all rows is 0.25-0.4%.
- Fresh-process runs: aws-lc-rs hedged sign 7.3-7.4%; in the first `default` repetition this crate's prepared-key rows have
  spreads of 12.1% (ML-DSA-44 prepared verify) and 10.9% (ML-DSA-65 prepared sign), a few slow rounds in a process that started
  at load average 1.9, right after the previous job; the second repetition of the same processes is at most 1.0%, and so
  is everything else except one 3.9% (`avx2` run 2, ML-DSA-44 prepared verify). The medians of the two repetitions differ
  by at most 1.6% (default).
- Two repetitions of each in-process binary differ by at most 1.8% (default), 1.9% (`avx2`) and 4.0% (v3, one libcrux row);
  two fresh-process repetitions by at most 1.6% (default), 2.9% (`avx2`) and 7.3% (v3, libcrux rows).
- The cross-implementation agreement check of `bench` (every implementation returns byte-identical keys and signatures)
  passed in the in-process runs. The one-process-per-implementation runs measure one implementation each, so they do not
  repeat it. Sign figures for the three sets depend on the message set through the number of rejection attempts (see above).

## Profile (category breakdown)

Sampling profiler (`bench/profile.sh`: `prof` built with the `nearcore` profile plus line tables and
`-C force-frame-pointers=yes`, 1000 Hz SIGPROF, 20 s per workload, pinned to CPU 1) and `bench/categorize.py`. Categories
follow the brief: Keccak (permutation, and sponge glue plus rejection parsing, which are reported together because inlining
moves time between them), NTT, pointwise, rounding/hints/norms, encoding, copies and other. The run profiles this crate's
default and `avx2` builds, mldsa-native AVX2 and libcrux AVX2, ML-DSA-65 and -87, deterministic sign and verify. The numbers
are shares of samples and microseconds per call *under the profiler* (frame pointers and sampling cost a few percent).

Read the profile with these limits in mind:

- The default-build profile of this crate was taken in a fresh process (it was the first implementation to run), so it is the
  slow state of "Process state": its NTT share is inflated. The in-process default-build breakdown, from a second profile run
  that executes `mldsa-native-avx2` first, is given below it.
- Category attribution uses the innermost frame with a known name. Inlined generic code (libcrux) and assembly leaves
  (mldsa-native's NTT and Keccak-x4 have no symbols and are attributed to their C wrapper) make the split approximate; libcrux
  AVX2 categories in particular move by tens of points between builds. For this crate, helpers such as
  `field::ct_select`, `wrapping_sub` and `small_reduce` are attributed to the category of the code they were inlined into, and
  that differs between the ML-DSA-65 and -87 builds (the -87 build has 19% of sign under "other" for this reason).
- Totals differ from the timing tables by profiler overhead. The AVX2 builds agree with the timings within 4%.

### What the leaf functions say (this crate, `avx2` feature, deterministic sign)

`bench/categorize.py --top 12` on the folded stacks: for ML-DSA-65 sign, `field::ct_select` called from `decompose`

the constant-time scalar helpers are 30% or more of AVX2 sign in both sets. mldsa-native AVX2 spends 1-2% in all of
rounding, hints and norms. In absolute terms for ML-DSA-65 sign the

against 2, and encoding 15 against 14 (mldsa-native's split between "encoding" and "copies, other" is not stable between

hypothesis, not a finding. The decompose/`ct_select` cost in the profile above fits it.

## Problems and limits

- The process-state effect above is unexplained; the report gives both states. The libcrux v3 rows carry +-7% process-to-process
  variation.
- aws-lc-rs: no deterministic sign, no context parameter, no prepared verify, random attempt counts (up to about 9% bias on
  the ML-DSA-87 hedged figure, above). Its C build flags are known only from the build script's inputs (see the implementations table). `-C target-cpu`
  does not reach it.
- The category profile for the default build is of the fresh-process state; category attribution is approximate for inlined
  and assembly code.
- The folded stack files behind the profile tables (about 680 KB) are not in `data/`; the tables themselves and the PROF lines
  are in `data/profile-*.log`, so `categorize.py` cannot be rerun from the repository alone. Rerun `bench/profile.sh` to regenerate.
- Single machine type (Zen 4 VM). Not measured: Intel, aarch64, wasm32. One key pair per set, hot caches, 64-byte messages.
- The in-process runs used binaries built at commit ebdfedc (before `--round-secs`, `--only` lists and `--prime-avx2` were
  added to the harness); the aws-lc-rs long-round run used a build at 3f19426. Library code and cells are identical.

## Exact commands

All on the build box through `rx` (the worktree is synced; `$ML_DSA_SCRATCH` is a directory under `~/rx/scratch`). Pinned CPU 1
is what `compare.sh` selected.

```
export ML_DSA_SCRATCH=$HOME/rx/scratch/bench-20261106
# 1. in-process run: builds default, avx2 and x86-64-v3 (nearcore profile), picks the idlest core, runs each pinned
rx submit bench-main -- 'export ML_DSA_SCRATCH=$HOME/rx/scratch/bench-20261106; bash bench/compare.sh 20261106'
# 2. second in-process repetition, same binaries
S=$ML_DSA_SCRATCH/ntt-bench-20261106
for v in default avx2 v3; do taskset -c 1 $S/bench-$v --label 20261106-$v-cpu1-rep > $S/$v.cpu1.rep.tsv; done
# 3. aws-lc-rs with 1.5 s rounds (default build)
taskset -c 1 $ML_DSA_SCRATCH/bench-aws --only aws-lc-rs --round-secs 1.5 --rounds 15 --lat 0 --label awslong-default-cpu1
# 4. one implementation per process, two repetitions (the binaries of step 1)
bash bench/isolated.sh $S 1 $ML_DSA_SCRATCH/isolated 2
# 5. profile (nearcore profile, pinned to CPU 1, 20 s per workload)
bash bench/profile.sh nc 1 20
#    in-process default-build profile of this crate: prof from step 5, mldsa-native-avx2 first
taskset -c 1 $ML_DSA_SCRATCH/profile-nc/prof-default OUT --secs 20 --impl mldsa-native-avx2,ours --ops keygen,sign-det,verify --sets 65,87
# 6. attempts per sign over the message set
(cd bench && cargo run --release --features internals --bin micro -- --rounds 1) | grep ^ATTEMPTS
# 7. tables (microseconds; D = bench/results/2026-11-06/data)
python3 bench/table.py report  D/inprocess-default.run1.tsv D/inprocess-default.run2.tsv D/inprocess-avx2.run1.tsv D/inprocess-avx2.run2.tsv D/inprocess-v3.run1.tsv D/inprocess-v3.run2.tsv D/aws-long-rounds.tsv
python3 bench/table.py fresh   D/fresh-default.run1.tsv   D/fresh-default.run2.tsv   D/fresh-avx2.run1.tsv   D/fresh-avx2.run2.tsv   D/fresh-v3.run1.tsv   D/fresh-v3.run2.tsv   D/aws-long-rounds.tsv
python3 bench/table.py compact <the 12 files above, fresh first>
python3 bench/table.py spread FILE ; python3 bench/table.py repeat FILE1 FILE2
python3 bench/categorize.py --table FOLDED... ; python3 bench/categorize.py --table-abs PROFLOG FOLDED... ; python3 bench/categorize.py --top 12 FOLDED
```
